# Experimental EIP-8288 profile

This branch activates dependency frames and separate block proofs at Bogota. It pins the
experimental leanVM profile reported by `alloy_eips::eip8288::PROFILE`. The EIP's protocol
verification key and dependency hash remain unsettled; this profile is for coordinated devnets.

Headers contain `dependencyProofHash` and `blockDepsHash`. Raw proofs are stored separately by
block hash, retained across restart and reorg, and verified before payload acknowledgement.
An unavailable proof is distinct from an available empty proof.

## Synchronization

Nodes fetch missing proofs before execution. Live block downloads prepare supplemental data
before returning blocks to the engine. Staged execution prepares its canonical range before
opening the database write transaction. Missing data remains retryable; it never establishes
that a block is invalid. Downloaded bytes must fit the 1 MiB limit and match the header's
Keccak commitment before storage. Block validation checks the aggregate's exact dependency claims.

The Bogota profile advertises eth/74 (EIP-8512), including when transaction gossip is disabled.
`GetDependencyProofs` (0x16) carries `[request-id, [block-hashes...]]`; `DependencyProofs`
(0x17) carries `[request-id, [proof-byte-strings...]]`. Empty entries mean unavailable data
unless the header commits to the empty proof. Short responses cover a prefix; the remaining
hashes are unserved and retryable. Entire responses are authenticated before storage.

Requests allow at most 1024 hashes. Serving runs off the network task with two concurrent
reads, a one-second cooldown per peer, and the 2 MiB response soft limit. Each proof is bounded
by EIP-8288's 1 MiB maximum before allocation or hashing. Missing or unresponsive peers are
retried; non-empty commitment mismatches disconnect the peer. Eth/74 retains eth/73 indexed
cell support and earlier versions remain available for negotiation.

## Wrapper admission and gossip

The existing `eip8288/1` capability carries bounded wrappers. Complete transaction entries use
pooled transaction encodings so blob sidecars survive admission and forwarding. Wrapper size
limits still apply to those complete encodings. Transactions already exchanged may use hash
references; an explicit recovery request restores complete entries.

Wrapper verification uses a bounded cache of successfully verified immutable evidence. A cache
hit reuses proof verification only; current transaction coverage and pool admission still apply.
Each peer may have at most one admission in flight, and the worker continues servicing events
and publishing aggregates while admissions run. Successful publication advances the selection
cursor, so an unchanged pool larger than one wrapper is served over successive batches.

## Compatibility boundaries

The wrapper capability remains a devnet transport rather than the eth/75 wrapper
announcement/retrieval protocol in EIP-8437. Proof bytes still require the same experimental
cryptographic profile, since EIP-8288 leaves its protocol constants unsettled.

The branch uses `newPayloadV7`, `getPayloadV7`, `forkchoiceUpdatedV6`, and the V3 payload-body
methods. Empty inclusion lists are supported; nonempty lists are rejected. Full FOCIL handling,
`getInclusionListV2`, eth/75 blob-data elision and cell retrieval, and finalized protocol
cryptographic constants remain outside this devnet profile.
